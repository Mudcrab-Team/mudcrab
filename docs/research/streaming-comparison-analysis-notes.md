# Streaming comparison analysis notes

The [protocol](streaming-comparison-protocol.md) was fixed before the main campaign. Its exact bytes and the runner were copied into the campaign's `campaign-source` directory and verified against the manifest's SHA-256 values. The four smoke launches are retained separately and excluded from the main estimates.

Primary movement and tail metrics assign each complete frame interval to its recorded ending phase, as specified in the protocol. The analyzer also retains `moving_prorated` and `tail_prorated` metrics, which split boundary intervals against the exact real-time route. This sensitivity calculation was implemented and checked on the smoke artifacts before the main campaign. Both versions are reported; the default decision uses the primary ending-phase metrics.

A completed route with pending work after its prescribed tail remains eligible for frame-pacing comparisons. Its readiness is censored, and the pending-work and desired-cell exposure remain outcomes. Excluding such a run from pacing could preferentially remove the slower-loading policy. Functional failures, timeouts, incomplete paths, changed inputs and truncated required traces remain visible and invalidate their affected estimates.

Desired-cell coverage reconstructs the committed cell set from the complete lifecycle timeline and intersects the camera's radius-two window with cells present in the converted database. It measures committed CPU cell data. Pending model, surface and arming queues provide separate count-seconds of delayed work inside committed cells. These observations do not certify drawing or pixel coverage.

OS RSS is sampled on the owned process at one-second intervals in every mode. Phase samples use the report's wall-time/elapsed-time anchor, with coverage ages reported. Sampled peaks are lower bounds. Adaptive reservation estimates are retained separately and are not measured RSS or GPU memory.

The benchmark report and measured-frame CSV cover route motion, or the stationary tail for a zero-speed smoke run. The streaming trace additionally retains all startup and tail frames. Route position and frame intervals use `Time<Real>`; process-launch startup timing includes initialization before the profiler begins.

The native binary was built once with the `quick` profile and the existing Metal terrain sampler compatibility patch. Its source overlays and SHA-256 are recorded in `build-receipt.json`. Every main arm uses that immutable binary. The result concerns the current test build on this Mac; release-build, first-person rendering and player collision qualification remain separate work.

An unrelated Cargo build began at 09:37:46 UTC on October 10, during movement in run 23, the adaptive arm of the first ablation block. The runner stopped before launch 24. The 20 primary runs had finished before that build. Before inspecting the affected movement results, we retained all three original ablation arms, excluded that whole block from paired estimates, and scheduled a replacement block in the same order. The remaining two blocks retain their planned order. This avoids replacing only one policy's observation. A second Cargo build prevented the first resume attempt before any game launched. The campaign resumed with the same binary, inputs, caps and preserved caches after that build finished. The original manifest and campaign sources remain available alongside the amended manifest and resume history.

The first aggregate falsely rejected four finished traces. A report snapshot recomputes its profiler-clock offset after the final trace sample, while both share the same real-time route clock. Comparing the earlier trace timestamp against the later report's converted tail timestamp therefore produced apparent gaps of 1–4 milliseconds. Completion now uses the final trace's own real-clock markers, phase and endpoint; genuine early or truncated traces still fail. All four affected records finish beyond their prescribed tail endpoint. Regression tests cover delayed report conversion, unchanged prorated metrics, genuine truncation and an early forged finished phase. The original aggregate is retained under `before-clock-fix-*` in the analysis directory.

The controlled run 31 first shows complete CPU observations at the end of frame 211. The route recognizes those observations in `PreUpdate` of frame 212, after a 200.94 millisecond real frame interval. Its warning preserves the distinction between first observed CPU readiness and the route's common settlement gate; primary startup latency uses the latter.
