> **Topic:** Spud `src/render`, `shaders/` and `src/fx`: GPU-driven submission, materials, shadows, water, sky, grass, far trees and post effects.

## Summary

- Spud renders Skyrim-like scenes through a Vulkan renderer with GPU-driven mesh submission, streamed assets, and explicit frame resources.
- Size measured from files: `src/render` has 46 files and 14,285 lines; `shaders/` has 89 files and 5,047 lines; `src/fx` has 7 files and 3,283 lines.
- Maturity: broad and technically mature implementation, with detailed shader recreation and GPU instrumentation. No renderer test suite was found in the inspected tree.
- The frame uses a dynamic-rendering HDR scene target, reverse-Z depth, optional 1/2/4/8x MSAA, and ordered opaque, terrain, alpha, sky, AO, decal, composite, water, and blend work.
- Bindless descriptors expose 65,536 texture slots. Per-frame descriptor sets avoid updates while submitted frames can still read them.
- GPU-driven draws batch instances by mesh/submesh and render state into indirect commands. Specialized pipelines remove unused material feature code.
- Skyrim shader families include lighting and effect shaders, with skin, hair, eye, parallax, environment map, glow, snow, projected texture, and multilayer paths.
- Shadows include sun cascades and local spot, hemisphere, and dual-paraboloid omni maps. Shadow maps are frame resources, so static-map caching is not established by the current code.
- Water, sky/weather, terrain, grass, far-tree impostors, particles, precipitation, volumetric lighting, reflections, AO, HDR exposure, bloom, tone mapping, and DOF have code paths.
- The stated image policy excludes TAA, temporal upscaling, frame generation, full-frame history resolves, and jitter. It uses 4x MSAA by default and allows effect-local temporal state.
- The 2026-11-13 rendering documentation describes deterministic current-view LOD and clean settled poses. That is a project requirement and design claim, not independent runtime proof.
- Largest liberties or gaps: parity is not proven by code inspection; shadow caching is not evident despite documentation's general example; performance documentation says its measurements were headless and need real-window checks.
- License caveat: Spud is MIT and Mudcrab is GPL-3.0-or-later. Borrow techniques and independently implement them; do not copy Spud code.

## Cross-area dependencies

- Engine/game view construction supplies `FrameInput`, `SpaceView`, environment/weather parameters, material data, draw lists, terrain, grass, water, particles, shadows, and skinning inputs.
- Renderer exposes `Renderer`, texture/mesh managers, uploader, GPU timings, counters, captures, shadow resolution, and offscreen target creation to engine and tooling callers.
- FX supplies effect definitions and random/table data. Renderer consumes prepared particle/effect draw data rather than owning all gameplay simulation.
- Imported asset and format code supplies mesh groups, material flags, textures, land cells, sky meshes, and water data. This review did not inspect those producer contracts in depth.
- UI and movie rendering use the swapchain/output and overlay paths; local maps and portal views reuse offscreen scene targets.
- Vulkan, SDL, VMA, GLM, and shader compilation/runtime support are external build dependencies.

## Liberties and deviations

1. **High — image reconstruction policy. Visible to a player.** Spud deliberately excludes TAA, temporal upscaling, frame generation, full-frame history resolve, camera jitter, and checkerboard rendering. It defaults to 4x MSAA. ## Open questions

- Does the renderer match retail Skyrim at fixed poses across materials, weather, exposure, shadows, water, and post effects? Cheapest resolution: use supported HDR/final captures with matching source assets/settings and compare regions against retail captures.
- What exact frustum/occlusion rules and LOD transition thresholds feed draw lists? Read the engine view-construction producer and compare to game-derived evidence.
- Are any shadow cache paths outside `renderer_shadows.cpp` or hidden in input construction? Trace `SpaceView` shadow data and `Lifetime::cache` call sites.
- Which Vulkan extensions/features are hard requirements versus optional fallbacks on each supported device? Trace physical-device selection and feature-chain checks in `device.cpp`.
- Are all special shader families and uncommon technique permutations exercised by tests or fixtures? Search scripted audit fixtures and use material-class output/captures.
- Does optional SMAA exist as implemented code or only as a possible policy choice? Rendering documentation says “optional ... only if it proves necessary”; no SMAA shader appeared in the inspected shader inventory.
- Does volumetric lighting or AO accumulate across frames in practice, and does each path settle deterministically? Trace every cross-frame resource creation against `device.cpp`'s allowlist and scripted fixed-step captures.
- Are reported performance gains representative in a visible window, across GPU vendors, and after present-path changes? Use documented real-window scenarios; no run was made here.
