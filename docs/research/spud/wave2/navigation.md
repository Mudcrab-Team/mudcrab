## Architecture

Space model. A "space" is the WRLD for an exterior cell and the CELL form itself for an interior: `Game::space_of_cell` returns the cell's parent if it has one, else the cell ([`src/game/game.cpp:233`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/game.cpp#L233)). Merged city worldspaces are separate spaces; the app widens the player's ground set with `space_ids` so a city region and its parent count as one walking ground ([`src/engine/app_ai.cpp:139-149`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/engine/app_ai.cpp#L139-L149)).

Navmesh ownership. `NavMeshes` indexes every `NAVM` by its parent CELL: exterior cells become `(WRLD, grid_x, grid_y)` keys from `XCLC`, interior cells become `CELL -> NAVM` lists ([`navmesh.cpp:75-94`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.cpp#L75-L94)). A NAVM whose parent is missing or not a CELL is dropped ([`navmesh.cpp:79-82`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.cpp#L79-L82)). Meshes are decoded lazily and cached by form id; the geometry is immutable after decode and the map alone is mutex-guarded ([`navmesh.cpp:118-148`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.cpp#L118-L148), [`navmesh.hpp:64-66`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.hpp#L64-L66)).

Three query layers:
1. `locate(space, point, reach)` picks triangles under a point. Interior: that cell's meshes. Exterior: the 3x3 cell block around the point ([`navmesh.cpp:174-187`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.cpp#L174-L187)). Per-mesh and per-triangle plan-view boxes prune candidates, then exact plane containment gives the height, else the nearest point on the triangle ([`navmesh.cpp:195-224`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.cpp#L195-L224), `40-71`).
2. `walk(spot, x, y)` steps the triangle under a moving point, up to 32 triangles per call, following `edges[]` or, when the triangle's flag bit for that edge is set, `edge_links[]` into another mesh — including another cell's mesh ([`navmesh.cpp:227-273`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.cpp#L227-L273)).
3. `path(from, to)` is an A* over (mesh, triangle) nodes with straight-line cost between edge midpoints and a distance-to-goal heuristic, then a funnel over the corridor's portals ([`navmesh.cpp:275-383`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/navmesh.cpp#L275-L383)).

AI owns agents, not spaces. `Agent` carries `space`, position, package pointer, resolved `AiLocation`, current path and a `NavSpot` cache ([`ai.hpp:113-196`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.hpp#L113-L196)). `Ai::update` gets the list of `high` actors (those in the player's attached cells) from the app and walks only those ([`ai.cpp:1555`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L1555), `1691-1713`); low-process actors think only when the hour changes, a few per frame, and are *placed* at their package location instead of walking ([`ai.cpp:1673-1679`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L1673-L1679), `476-484`, `648-650`).

Package selection is a priority scan: forced (tests) > quest alias packages > NPC's own `PKID` list (through a TPLT template with the "Use AI Packages" bit) > default list (`DPLT` or `DefaultMasterPackageList` 0x00021E81) > keep the current package ([`ai.cpp:360-381`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L360-L381), `281-324`). A package's procedure kind is inferred from its template record's editor id by string prefix, else from the last procedure name in its own tree, else `stay` ([`ai.cpp:44-56`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L44-L56), `197-234`).

Cross-space travel is a two-stage state machine, not a cross-cell path:
- `walk` finishes a path, then sees `location.space != a.space`, asks `door_towards(from, to)` for the first door on a breadth-first search of the *space graph* built from REFR `XTEL` records, paths to that door's position, stores `leg_door`, and on arrival teleports the agent to the door's `XTEL` arrival point and heading ([`ai.cpp:942-968`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L942-L968), `795-867`).
- If no door chain exists, or the path to the door fails, the agent is placed directly at its goal: "the game moves them too" ([`ai.cpp:958-964`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L958-L964), `1574-1581`).
- Off-screen followers get a cheaper version: ETA = distance / run speed, then teleport through the first door ([`ai.cpp:1763-1794`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L1763-L1794)).

Threading. Door indexing, path searches, mesh warm-up and arrival grounding all run on `std::async` background threads; results are collected on later ticks. Searches are capped (4 total, 2 for low actors), and in replay mode a search completes after 6 ticks so runs match ([`ai.cpp:869-882`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L869-L882), `34`, `1562-1585`, `1642-1671`).

```
REFR XTEL ──build_doors──> m_doors{ref -> dest space, arrival}
      │                          │
      │                          └─ door_towards(BFS over spaces) ─┐
      ▼                                                           │
NAVM NVNM ──forms::navmesh──> NavMeshes{space -> meshes}          │
      │                        │  locate / walk / path / middle   │
      │                        ▼                                  │
 PACK ─> AiPackage ─> AiLocation ─> request_path (background thread) ─> path │
      │                     │                                    │
      └─ select/qualify ────┴─ walk (high actors only) ───────────┴─> change_space
                                                                     (teleport at door)
```

## Port notes

Ordering and coupling:
1. Decide the space identity function first (`space_of_cell`). Every other rule depends on it: navmesh index, door graph, roster, follower catch-up. Mudcrab's `references.cell_id` plus `cells.worldspace_id` already yields it in SQL.
2. Locate before path. A path request with an unreachable endpoint must fail cheaply and be retried with a deadline; spud's 2 s `no_path_until` is a reasonable floor.
3. Keep the query off the main thread and make completion tick-counted, not time-counted, or runs stop matching. Spud learned this (`m_replay`, [`ai.cpp:1562-1591`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L1562-L1591)).
4. Cross-space travel is a leg to a door plus a space change. If a load takes several frames in Mudcrab, an NPC door leg must wait for the destination cell to be resident; spud avoids the problem by teleporting, which is not acceptable in view.

Hidden coupling and constants worth knowing: 4096 units per exterior cell; the 3x3 locate window; 32 walk hops; 60000 node cap; 4/2 search budget; 512 and 256 locate reaches; body radius 40 for steering; 1 s stuck window, error ratio 0.9 (stuck below 10% of wanted movement; corrected at publication), 3 failures then warp; 150 units ForceGreet range; 5000 units door unlock radius; 6 replay ticks. `NavMeshes::middle` is the only "in cell" anchor and it is a vertex, not a polygon centroid.

Liberties that will bite:
- Link `type` is ignored, so ledges and disabled portals are walkable.
- `deleted` triangles are walkable.
- NAVM door triangles are ignored; doors are found only through REFR `XTEL`, so a navmesh door with no teleport (or a teleport with no `DOOR` base) behaves differently from the game.
- Locked doors are crossed; there is no lock or ownership check in `door_towards`.
- Off-screen actors teleport at package start, so they appear rather than arrive.
- The A* can return a sub-optimal path because stale queue entries are re-expanded with their old cost.
- The `fAIEngergyLevelMult` typo silently disables one setting.
- `const bool to_high = false; (void)to_high;` at [`ai.cpp:944-945`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L944-L945) is dead residue of a removed high/low handoff at doors.

Minimal vertical slice that proves the subsystem: one interior cell whose navmesh has at least two triangles and one portal; query a path across it headlessly; assert the exact corner list and total length against a hand-computed funnel result; then repeat across an exterior grid boundary using a two-NAVM `edge_links` fixture; then a door pair. If those three pass, link traversal, funnel and space switching are all proven. Packages are a separate slice: one NPC, one Travel package, one door, and an assertion that the agent ends in the destination space with the `XTEL` arrival position.

## Test ideas

Deterministic, headless, fixture-first:

1. **Two-triangle funnel.** Synthetic NAVM: 4 vertices, 2 triangles sharing an edge, no edge links. Path from a point in A to a point in B must be `start, end` when the shared edge is not a corner, and include the shared portal endpoint when the geometry makes it one. Assert point count and each coordinate to 1e-3. No randomness, no clock.
2. **Portal crossing with a link.** Two NAVMs in adjacent exterior grid squares, `edge_links` both ways, triangles at the shared boundary. Assert the path has points in both meshes, and that `walk` moves the spot's `mesh` id across. This is the two-cell probe from Mudcrab issue #399.
3. **Link-type fixture.** Same geometry, `type = enable_disable_portal` and, separately, a `deleted` flag on the only middle triangle. Record spud's answer as the deviation baseline; then decide Mudcrab's rule explicitly (block, or match spud) and assert the decision. Do not silently inherit the liberty.
4. **Door leg.** Two interior cells joined by an `XTEL` pair. A Travel package whose location is the far cell must produce exactly one leg, and the final position must equal the `XTEL` arrival, not the destination door's position. Assert no path point lies in the far space.
5. **No door.** Two interior cells with no `XTEL`. Assert the explicit policy: one-tick placement (spud) or a queued load request (probably Mudcrab).
6. **Vanilla package fixture.** Extract three PACK records with known behaviour: one Sandbox, one Travel, one Patrol with three linked markers. Assert mode, allow bits, radius, and the marker order. The typed payload from `ai.json` already gives every field.
7. **Schedule fixture.** Fix the clock at one hour and assert the selected package form id for a named NPC. Without a documented vanilla expectation this is a regression test, not a parity test; label it as such.
8. **Replay determinism.** Run 200 ticks twice with the same seed and actor set; assert identical `digest` and identical per-agent path lengths. Spud's `digest`/`dump` ([`ai.cpp:503-537`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/src/game/ai.cpp#L503-L537)) is the model.
9. **Detection arithmetic.** Table-driven unit test of `detection_level` with one variable changed at a time (distance, angle, LOS, light, sneak, sleeping observer). No world needed.
10. **Grounding.** Place an actor 500 units above a known navmesh triangle, run the arrival path once, assert it lands on the triangle plane and not on terrain.
11. **Decoder cross-check against spud's own dump.** `skytool` already writes per-NAVM `FormID, triangle count, cover count`, then each triangle as 8 little-endian `u16` words (`vertices[3], edges[3], flags, cover_flags`), then the cover list ([`apps/skytool/cmd_gamedump.cpp:240-264`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/apps/skytool/cmd_gamedump.cpp#L240-L264)), and its JSON dump carries `vertex_sum`, `index_sum`, `triangle_sum`, `cover_sum` and the edge links ([`:149-181`](https://github.com/chasmlol/spud/blob/8c9904207a5c573a0193fb903fb5c433f127f102/apps/skytool/cmd_gamedump.cpp#L149-L181)). Run that once over vanilla data, then assert Mudcrab's `world_extras.rs` decoder reproduces the same counts and sums for the same FormIDs. This is a cheap, deterministic decoder oracle that needs no game launch and no navmesh runtime.

Fixture sources: Mudcrab's existing primary manual area is Riverwood (`SPEC.md:14`), so use one Riverwood interior (for example the trader) for the interior fixture and the Riverwood exterior grid square for the exterior one, plus the door pair between them. Exact cell FormIDs were not verified in this audit.

## Open questions

- Does vanilla Skyrim path across a load door in one path, or as a leg plus a load? Spud assumes legs. Neither the code nor the docs in the repository settle it; the referenced "spec" sections are absent.
- Which PACK procedure types actually occur in Skyrim.esm and its masters, and what share map to spud's 10 executed modes? Needs a decoded corpus count, not a source read.
- Are non-`DOOR` references with `XTEL` real load doors in the game data? Spud accepts them, Mudcrab's converter excludes them by join. One query over a converted database settles it.
- Does `NAVM.door_links` ever disagree with REFR `XTEL` in vanilla data? If it does, which one wins for AI?
- Is the 3x3 exterior locate window large enough for long straight paths, and does a path that leaves it still resolve its final spot? The path itself follows links, but `locate` at the ends does not.
- Which Mudcrab milestone owns navigation? The roadmap Phase 4 page names no navigation deliverable, and `#556` (named by the wave-2 plan) had not been read when this report was written, so its scope is unknown here.
- Does Mudcrab's runtime database already carry a typed PACK payload the engine can read without a new decode? `references` and `records` were inspected only at the schema level.
